# Public RFQ intake

Each active `WEBAPP` channel identifies one branch's public intake. The API resolves only that
channel's supplier identity on the owner pool, checking the account and branch are active, then
uses the resolved account and branch for all tenant-scoped work. Request bodies cannot select a
tenant, branch, seller, or client profile.

The customer form lives at `{WEB_WEBAPP_URL}/rfq/{channelId}`. Obtain the branch's `WEBAPP`
channel ID through the existing authenticated `GET /v1/channels` endpoint with `X-Branch-Id`;
there is no public branch directory or additional backoffice channel settings screen.
Migration `00050_public_rfq_channels.sql` provisions missing WEBAPP channels for existing branches;
new branches receive all four intake channels in their creation transaction. Apply it with
`pnpm db:migrate`. Its rollback preserves channels to retain request history.

The form always starts with blank customer fields, followed by a choice between a text order and
one file. Editing the contact returns to the first step within the same in-memory submission;
receipt clears those values. A page reload or another request starts from blank fields again.

| Method | Path                                           | Purpose                                      |
| ------ | ---------------------------------------------- | -------------------------------------------- |
| `GET`  | `/v1/public/rfq-channels/{channelId}`          | Supplier name, branch name, and logo URL     |
| `POST` | `/v1/public/rfq-channels/{channelId}/requests` | Submit text as JSON or one file as multipart |

Submissions require `request_id` (UUID v4), `tax_id` (CUIT), `name`, and `email`. `phone` is
optional. JSON submissions carry `text`; multipart submissions carry exactly one `file` part
and no text. Existing RFQ text and storage size limits apply. Accepted file formats are the same
as the seller's file intake. This endpoint has a separate rate-limit lane using `RATE_LIMIT_AI_MAX`.

`request_id` identifies a submission retry, not a customer or session. The browser must reuse it
only when retrying the same payload. A durable `inbound_channel_message` reservation retains the
contact snapshot and a payload fingerprint, and an advisory lock serializes retries. A changed
payload with the same ID returns `409`. RFQ IDs are generated by the backend.

The customer receives only `{ "received": true }` after durable reception. Internal identifiers,
model results, and client profile data are never included. No customer lookup, session cookie,
saved browser profile, automatic client creation, or contact overwrite takes place. The seller
confirms client association through the existing accepted-sale workflow.

Text uses the existing inbound RFQ pipeline with no assigned seller. A provider failure leaves
the retained request available to the seller and does not revoke its receipt. Files are retained
as pending attachments for the existing attachment sweep; run the configured scheduled attachment
job to process them. A failed storage operation is not acknowledged and can be retried without
creating another RFQ. A retry after successful storage does not store a second attachment.

Authorized RFQ detail responses include `public_contact`, the customer-declared contact snapshot
from that request. It is account and branch scoped and does not establish identity or ownership of
an existing client profile. Public destination and submission responses use `Cache-Control: no-store`.

`public_original_text` and `public_attachments` accompany those declarations in the authorized RFQ
detail. Attachment links are freshly signed through the existing storage service. The backoffice
maps the new fields into `publicRequest` before rendering contact and source material together.

For per-customer IP limits behind a reverse proxy, configure `WEB_TRUSTED_PROXY_HOPS` on the
webapp to match the trusted ingress chain. The BFF forwards only that hop's valid IP address;
with zero (the local default) it forwards none. The API must separately trust the BFF peer through
`RATE_LIMIT_TRUSTED_PROXY_CIDRS` and `RATE_LIMIT_TRUSTED_PROXY_HOPS=1`. Without this deployment
configuration, all submissions forwarded by one BFF share its IP allowance.
